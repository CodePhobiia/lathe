    Release gates — v0.2.0rc1¶

    Version: 0.2.0rc1 (pre-release reference compiler scaffold) Captured: 2026-04-28 Owner: Tal Merri (@talmerri) Worktree: .claude/worktrees/readiness-pass-v020rc1/ (paths in this document are written relative to the repo root unless otherwise noted) Branch: worktree-readiness-pass-v020rc1 Scope: Phase 6 of the v0.2.0rc1 readiness remediation pass — record every release-gate decision (mypy, dependency vulns, security scanners, lint, tests, docs, package, branch protection) with evidence paths, exception cross-references, and requires-human follow-ups.

    This document is the canonical Phase-6 gate record. The aggregator doc (docs/release/evidence-v0.2.0rc1.md Phase 6 section) cross-links to it. Release exceptions accepted in this pass are registered in docs/release/decision-log-v0.2.0rc1.md.

    Nothing in this document changes the release timeline; v0.2.0rc1 remains under the launch freeze recorded in docs/release/evidence-v0.2.0rc1.md until every Phase 0–18 task in readiness-tasks.md is green or has a recorded exception.

    • Command: .venv/Scripts/python.exe -m mypy lathe/ (run from the worktree root)

    1.5 Gradual typing plan¶

    The following sub-packages are proposed as the first wave to reach mypy-clean before v0.2.0 final, ordered by existing test coverage and public-surface risk. They are deliberately small, well-tested, and form public-ish boundaries so the typing investment does the most work.

    1. lathe/parser/ — language-grammar boundary; small, regression-tested, public surface for users authoring .lth. (Currently 2 files with errors.)
    2. lathe/runtime_config.py — provider-config boundary; covered by tests/test_runtime_config.py and the provider_config coverage gate in [tool.lathe.coverage_gates] (fail_under = 75).
    3. lathe/net.py — egress boundary; covered by the security coverage gate (fail_under = 75). Wrong typing here can leak credentials.
    4. lathe/telemetry.py — privacy-sensitive; covered by the telemetry coverage gate (fail_under = 80).
    5. lathe/publish/ — release-pipeline boundary; covered by the security coverage gate. Two files currently emit errors.

    Wave 2 (after wave 1 lands and CI gates them): lathe/checker/ (per the 70% coverage gate), lathe/planner.py (90% gate), lathe/resolver.py (90% gate), then lathe/cli/ last because of its size (24 affected files).

    The gradual-typing plan is not enforced by CI in this RC. Tracking issue: requires-human: open a tracking issue named "v0.2.0 final: mypy clean wave 1 (parser, runtime_config, net, telemetry, publish)" and link it fromdocs/next_version_roadmap.mdE13.

    2. Dependency vulnerability¶

    Phase 3 captured the canonical pip-audit transcripts in evidence-bundle-v0.2.0rc1/pip-audit-runtime.txt and pip-audit-dev.txt. Both transcripts identify two CVEs:

    package version id fix
    lxml 5.4.0 CVE-2026-41066 6.1.0
    pip 26.0.1 CVE-2026-3219 (no Fix Versions in pip-audit DB)

    2.1 lxml — CVE-2026-41066¶

    • Investigation: evidence-bundle-v0.2.0rc1/lxml-investigation.txt.
    • Disposition: NOT a release blocker. NO release exception required.
    • Why: lxml is not declared anywhere in pyproject.toml (dependencies or any optional-dependencies.*) or any requirements*.txt, and is not imported anywhere in lathe/ or scripts/. Every reverse-dependency on lxml is gated behind a third-party extra (beautifulsoup4[lxml], cyclonedx-python-lib[validation], mypy[reports], networkx[extra], tifffile[xml/all/test], trimesh[easy]); none of those extras is selected by lathe's manifests.
    • A clean pip install lathe==0.2.0rc1 does not pull lxml.
    • The lxml 5.4.0 in the audit + SBOM is a stale dev-venv install. The disposition is recorded in pip-audit-runtime.txt under the appended ## Phase 6 follow-up (2026-04-28) section.

    2.2 pip — CVE-2026-3219¶

    • Investigation: evidence-bundle-v0.2.0rc1/pip-version.txt.
    • Disposition: release exception EXC-PHASE6-PIPCVE-001 (registered in decision-log-v0.2.0rc1.md).
    • Why: pip-audit reports no Fix Versions for this CVE. The newer pip 26.1 is installable but does not carry a documented advisory-fix marker for CVE-2026-3219. Upgrading is therefore opportunistic, not curative. pip is build/install tooling local to the venv, not a Lathe runtime dependency, so the CVE does not affect users of pip install lathe==0.2.0rc1.
    • Removal target: track upstream advisory closure; rerun pip-audit when pip-audit publishes a Fix Versions field for CVE-2026-3219.

    2.3 Re-run plan¶

    This pass does not rerun pip-audit (the canonical run is Phase 3 + the Phase 6 follow-up notes appended to pip-audit-runtime.txt). A regenerated transcript would contain the same two findings under the existing dispositions; rerunning would add noise without changing the record.

    3.1 Bandit findings (full list)¶

    All eight findings are subprocess-related (B404, B603, B604), which is expected for a compiler that shells out to Blender / xatlas / git. None is in user-input handling code. No # nosec suppressions are in use anywhere — the count is zero.

    sev/conf id rule path:line
    LOW/HIGH B404 subprocess import lathe/capabilities.py:15
    LOW/HIGH B603 subprocess call w/o shell lathe/capabilities.py:93
    MEDIUM/LOW B604 function call with shell=True parameter lathe/cli/completions_cmd.py:217 (false positive — line is raise ValueError(_UNSUPPORTED_SHELL_MESSAGE.format(shell=shell, supported=supported)); the literal shell=shell keyword arg to .format() triggers Bandit's pattern, not an actual subprocess call)
    LOW/HIGH B404 subprocess import lathe/core/stages/topology.py:19
    LOW/HIGH B404 subprocess import lathe/subproc.py:25
    LOW/HIGH B603 subprocess call w/o shell lathe/subproc.py:204
    LOW/HIGH B603 subprocess call w/o shell lathe/subproc.py:231
    LOW/HIGH B603 subprocess call w/o shell lathe/subproc.py:252
    • Disposition: NOT a release blocker. All seven B404/B603 items are by-design — Lathe deliberately spawns Blender/xatlas/git as subprocesses; the project's secure subprocess wrapper lives in lathe/subproc.py and is covered by the sandboxing and security coverage gates. The single MEDIUM-severity B604 is a documented false positive (rule pattern-matched on the keyword argument name shell= passed to str.format(); no shell is invoked).
    • No release exception required; no # nosec suppression added (we prefer to leave Bandit's signal visible rather than mask it).
    • Optional follow-up (NOT a v0.2.0rc1 blocker): file an issue at https://github.com/PyCQA/bandit/ for the B604 false-positive pattern, OR rename the keyword argument in lathe/cli/completions_cmd.py to avoid the trigger. Tracked as requires-human: H42.

    6. Docs — mkdocs --strict¶

    • First run: failed with 3 warnings → Aborted with 3 warnings in strict mode! (exit_code = 1). Evidence: evidence-bundle-v0.2.0rc1/mkdocs-strict.txt.
    • Root cause: three Markdown files used relative paths to SECURITY.md that resolved outside the docs tree (../SECURITY.md, ../../SECURITY.md). SECURITY.md lives at the repo root and is not exposed via mkdocs gen-files, so mkdocs strict treats those as broken links.
    • Fix applied in this pass (per the brief's allowance for "obvious broken-link errors that point at files we know exist"): rewrote the three links to the canonical https://github.com/talmerri/lathe/blob/main/SECURITY.md URL pattern already used by docs/index.md:34. Files touched:
    • docs/privacy.md:124
    • docs/terms.md:21
    • docs/release/telemetry-verification-v0.2.0rc1.md:53
    • Re-run: passed (exit_code = 0, "Documentation built in 17.76 seconds"). Evidence: evidence-bundle-v0.2.0rc1/mkdocs-strict-rerun.txt.
    • Disposition: pass. No release exception required.
    • Notes: mkdocs also emits an INFO-level message about terms.md:19 ../LICENSE being an unrecognized relative link; this is INFO, not WARNING, and does not abort strict mode. It is left unchanged in this pass to avoid scope creep.
