    Product experience — v0.2.0rc1¶

    Version: 0.2.0rc1 (pre-release reference compiler scaffold) Last reviewed: 2026-04-28 Owner: Tal Merri (@talmerri) Reviewer: requires-human (no second reviewer named yet) Host: Windows 10 Home Single Language 10.0.19045, Python 3.13.13, project-local virtual environment.

    This document captures Phase-7 product-experience evidence for the v0.2.0rc1 readiness remediation pass: time-to-first-value (TTFV), first-run friction, unhappy-path diagnostic quality, gallery / canonical-build verification, viewer / engine validation, and accessibility / i18n posture.

    It pairs with:

    • docs/release/evidence-v0.2.0rc1.md — release-evidence index
    • docs/release/decision-log-v0.2.0rc1.md — non-goals, forbidden public claims
    • docs/release/known-bugs-v0.2.0rc1.md
    • docs/error_codes.md — semantic CLI error-code table

    All evidence transcripts and copied build reports live under docs/release/evidence-bundle-v0.2.0rc1/.

    Activation moment (TTFV)¶

    The TTFV activation moment for v0.2.0rc1 is defined as:

    A user runs lathe build examples/courier_drone.lth courier_drone --out tmp_ttfv and observes certified=true in tmp_ttfv/courier_drone/build_report.json.

    It composes three commands: doctor (env probe), check (parse), build (full pipeline). The single deciding signal is the boolean certified field on the resulting build_report.json.

    TTFV measurement¶

    Captured 2026-04-28 on the Windows host described above. Raw transcript (stdout + time output) is in evidence-bundle-v0.2.0rc1/ttfv-windows.txt.

    step command wall-clock notes
    1 python -m lathe.cli doctor 46.305s first call exercises shape-provider probes (hunyuan2_1_http_v1, vggt_local_v1, reference_conditioned_v1), Blender --version invocation, xatlas import. Most of the wall-clock is provider probing and the Blender subprocess.
    2 python -m lathe.cli check examples/courier_drone.lth 1.937s parse + semantic checks; ok=true, no diagnostics.
    3 python -m lathe.cli build examples/courier_drone.lth courier_drone --out tmp_ttfv 3.733s certified=true, score=0.879435 ≥ threshold=0.86, all stages green.
    total — ~51.97s activation reached on first try.
    host TTFV source
    Windows 10 (this run) ~52s direct measurement
    macOS requires-human not measured here
    Linux requires-human not measured here

    requires-human: macOS + Linux TTFV measurement (CI or maintainer host).

    The first-run cost is heavily dominated by doctor. Once doctor has been run, subsequent builds are <5s. This is acceptable for a pre-release reference scaffold.

    First-run friction inventory¶

    Walked the README install steps end-to-end on this Windows host. The following decisions / clicks / requirements stand between a fresh user and a certified build:

    friction severity recommendation
    Bootstrap requires running scripts/bootstrap_local.ps1 -Dev -Export (or the bash equivalent) — no one-line pipx install path is available pre-PyPI. medium Document — already covered in README install section. The pre-PyPI status is a deliberate non-goal (EXC-PHASE3-PYPI-TP-002).
    Optional-extras (Blender, xatlas, vggt, geometry) selection. README documents these as optional but a fresh user must read the table to decide whether to install them. Without them, the conservative offline path runs (still certifies). low Document — already in README "Optional dependencies" matrix. Accept.
    python -m lathe.cli vs. lathe console-script: the latter requires the editable install to be active (pip install -e .). New shells without the venv activated must use python -m lathe.cli. low Document — both forms are listed in CLAUDE.md and docs/canonical_commands.md. Accept.
    Visual Studio Build Tools requirement. xatlas / manifold3d / Pillow on Windows can require MSVC build tools when no wheel is available. The current pin (xatlas>=0.0.11) ships wheels for 3.11 + 3.12 on Windows; the venv on this host runs 3.13 and pulled xatlas==0.0.11 successfully — so Build Tools were not needed in practice. low Document — README "Optional dependencies" should call out which extras require Build Tools on which Python version. requires-human: confirm wheel availability matrix on PyPI for 3.11 + 3.12 across xatlas / manifold3d / scikit-image / torch.
    Runtime-config decision: a fresh user does NOT need a runtime config to certify a hero example — the conservative path is the default. The runtime-config affordance is only required to opt into Hunyuan HTTP, VGGT, or auto-learned modes. low Already correct. README and docs/cli_reference.md make this clear. Accept.
    lathe doctor first-run time (~46s) is dominated by provider probing. A user with no network or Hunyuan server running gets a Hunyuan health: unavailable (http://localhost:8081) line followed by a recommended action. low Accept — the diagnostic is correct and the requires-human: recommended-action is Start or fix the configured Hunyuan HTTP server. Consider documenting expected wall-clock so first-run users do not assume the doctor is hung.
    Output-path safety guard: --out is rejected if it resolves outside the working tree, unless LATHE_ALLOW_EXTERNAL_OUT=1. New users with the habit of building into ~/Desktop/... or C:\Temp\... will hit this. The diagnostic includes an actionable next step. low Accept — diagnostic is good. README "First build" example uses an in-tree dist/ path which avoids the trap.
    Python-version drift: this host runs Python 3.13.13 in the venv even though pyproject.toml classifiers list 3.11 + 3.12 only. requires-python = ">=3.11" allows 3.13, but the support matrix and decision log explicitly say "Python 3.13 / 3.14 not supported". medium requires-fix-before-launch: reconcile. Either (a) bring the support matrix in line with the broader pin (>=3.11 already permits 3.13), or (b) tighten the pin to >=3.11,<3.13 to match the support matrix's promise. The current state is misleading.
    Doctor's Setup checks block reports every check as "ok" with the negative-form description still attached (virtualenv_active: ok (No active virtual environment was detected.)). The mismatch is a minor UX defect. low requires-human: confirm whether the cosmetic mismatch is intentional. Not launch-blocking.

    Summary: the pre-first-asset path is short for the conservative offline flow. The two friction items worth preserving as findings are the Python-version support drift (requires-fix-before-launch) and the doctor cosmetic-mismatch in the setup-check block (requires-human to triage).

    CLI exit codes¶

    docs/error_codes.md is comprehensive. Confirmed coverage for the cases this phase requires:

    case covered? code
    success yes 0 (implicit; documented in exit-code table)
    parse error yes lathe.cli.parse_error (exit 1)
    check failure yes folded under lathe.cli.error (exit 1) — semantic checks raise LatheError which the top-level handler maps to this code
    certification failure yes — folded under lathe.cli.build.build_failed when the build reports certified=false AND repair rounds exhaust lathe.cli.build.build_failed (exit 1). requires-human: confirm whether a certified=false outcome should keep exit 0 (build succeeded but did not certify) or exit 1 — docs/error_codes.md does NOT pin this distinction.
    provider unavailable (strict) yes lathe.cli.build.provider_fallback_blocked, lathe.cli.build.provider_failed (both exit 1)
    file not found yes lathe.cli.file_not_found (exit 2)
    output safety reject yes lathe.cli.build.unsafe_out_path (exit 2)
    usage error yes lathe.cli.usage, lathe.cli.unknown_command (both exit 2)
    optional dep missing yes lathe.cli.inspect.trimesh_missing (exit 3) — exit 3 is the "optional-dep gap" lane

    requires-human: document the boundary case "build succeeded but did not certify" — does the CLI exit 0 (build was honest) or exit 1 (cert is a hard gate)? The current code path runs lathe.cli.build.build_failed only when BuildError is raised, so a cert miss without exception is silent on exit code. Pin this in docs/error_codes.md before launch.

    Machine-readable output schema¶

    lathe doctor --json and the --report json build mode produce stable top-level shapes, but NO explicit schema_version field is present:

    • build_report.json top-level: asset, kind, out_dir, certified, backend_stack, selected_backends, runtime_config, stage_bundles, outputs, manifest_path, trace_path, score, threshold, repair_rounds, optimize. No schema_version / version key.
    • package_manifest.json top-level: includes version: "0.1.0" (likely meant to be the manifest schema), but it is not labeled schema_version and the same key name is overloaded by other documents in the bundle.
    • lathe doctor --json top-level: no schema_version.

    requires-human: add an explicit schema_version (e.g. "lathe.build_report.v1") to build_report.json, package_manifest.json, trace_manifest.json, and lathe doctor --json output before agent-builder Persona C ratification. Stable schemas with no version field are a compatibility risk for downstream agents that will pin against them.

    Automated Godot test plan (draft)¶

    requires-human: headless GUT (Godot Unit Test) automation plan. Open items:

    • pick a Godot binary distribution and pin its SHA in the dev-dependency matrix (Godot 4.3 LTS is the current stable target).
    • write a gut.cfg that loads the addon, imports a known canonical GLB bundle (the 02-courier_drone archive copied from tmp_gallery_phase7/), and asserts mesh / material / LOD invariants.
    • wire a CI job that downloads the pinned Godot, runs --headless --script res://addons/gut/gut_cmdln.gd -gtest=res://test/lathe_addon_test.gd, and uploads the test report.
    • gate the job on a label / dispatch (NOT every PR, since Godot is out of launch scope and the binary download is heavy).

    This draft is written down only so the work is captured. It is not in the v0.2.0rc1 launch path.

    Decision¶

    Manual-only Godot tests do NOT block public launch of v0.2.0rc1. Reason: the Godot addon ships in this release as alpha (V0.3 scope per docs/roadmap_public.md) but submission to AssetLib is explicitly a non-goal for v0.2.0rc1 (docs/release/decision-log-v0.2.0rc1.md). Manual smoke quality is therefore not the launch quality bar; it is a forward-looking-confidence signal for V0.3.

    Accessibility, internationalization, platforms¶

    Accessibility¶

    Scope: CLI text + generated HTML reports + docs site (mkdocs-material).

    • CLI text accessibility — text-only stderr / stdout, no ANSI required for content (color is TTY-aware via the standard library patterns in lathe/cli/_common.py). Screen readers should consume the output as plain text. requires-human: walk a screen-reader session through one full build invocation as a sanity check.
    • HTML report accessibility (axe-core / pa11y WCAG 2.2 AA audit) — lathe build … --report html is the affected surface. Tool not installed on this host. requires-human: run pa11y or axe against a generated HTML report (e.g. tmp_gallery_phase7/02-courier_drone/courier_drone/<report>.html if the html report is captured) before public launch.
    • Docs site (mkdocs-material) keyboard-navigation + contrast audit — not run in this pass. requires-human: keyboard-only navigation pass, contrast check (WCAG 2.2 AA) on the rendered docs site before public launch.

    Internationalization¶

    Out of scope for v0.2.0rc1. Localization is not supported. Recorded as non-goal-by-default — language surface, error messages, and docs are English-only.

    Non-ASCII paths¶

    Tested 2026-04-28 on this Windows host: created a directory named tmp_nonascii_тест (Cyrillic), cd-ed into it, and ran python -m lathe.cli check ../examples/courier_drone.lth. Result: exit 0, ok=true, no diagnostics. Non-ASCII path support works for the basic check command path. requires-human: repeat with a build that writes outputs into a non-ASCII path (the tmp_* prefix in the gitignore stripped, but the safety guard accepts any in-tree path), and with a non-ASCII venv install location — those broader scenarios were not exercised here.

    Python version support¶

    pyproject.toml declares requires-python = ">=3.11", classifiers list Programming Language :: Python :: 3.11 and … 3.12 (3.13/3.14 are NOT listed). docs/release/decision-log-v0.2.0rc1.md non-goals row says "Python 3.13 / 3.14 not supported".

    This host runs the venv on Python 3.13.13 (because the .venv/Scripts/python.exe points at the system Python 3.13 install). All evidence captured in this pass therefore came from a Python version that the support matrix does not promise. requires-fix-before-launch: reconcile by either tightening the pin to >=3.11,<3.13 (matches the support matrix) or by extending classifiers + the support matrix to acknowledge 3.13 as a permitted runtime. The current "permitted by requires-python but excluded by classifiers + support matrix" state is misleading.

    Summary¶

    • TTFV (Windows): ~52s for first-run; <5s for subsequent builds. certified=true on the courier_drone hero.
    • First-run friction: 9 items inventoried; 1 requires-fix-before-launch (Python 3.13 support drift), 2 requires-human (cosmetic doctor mismatch, wheel-availability matrix audit). Remainder accept-as-documented.
    • Unhappy-path walks: 4 PASS (good diagnostics), 2 requires-human (cert-failure example, provider-timeout host), 1 requires-fix-before-launch (catalog labeling drift on tutorial_bookshelf).
    • CLI exit codes: comprehensive table in docs/error_codes.md, with one open question — exit-code semantics for "build succeeded but certified=false" — captured as requires-human.
    • Machine-readable output schema versioning: no schema_version field on build_report.json / package_manifest.json / lathe doctor --json. requires-human: add before agent-builder Persona C ratification.
    • Gallery / canonical builds: 5/5 PASS (cert=true, full artifact bundle). Durable JSON evidence copied to docs/release/evidence-bundle-v0.2.0rc1/gallery/; binaries left in tmp_gallery_phase7/ for lead inspection. requires-human: archive binaries to release-asset bucket before public launch.
    • Engine + viewer validation: all requires-human (need glTF Sample Viewer / usdview / Houdini / Godot host). Godot addon explicitly OUT of v0.2.0rc1 launch scope per decision-log; manual-only matrix does NOT block launch.
    • A11y / i18n / platforms: docs-site WCAG audit, HTML-report axe/pa11y, macOS / Linux runs all requires-human. i18n is out of scope by decision. Non-ASCII path test PASS on Windows for lathe check.
