    Compliance Review — Lathe v0.2.0rc1¶

    This document is a self-assessment. No qualified counsel has reviewed v0.2.0rc1 as of 2026-04-28. Public launch is BLOCKED until counsel review is complete OR a launch exception is recorded with named owner, justification, and removal target. — requires-human: counsel review.

    Scope: the lathe Python package and CLI at version 0.2.0rc1, distributed under Apache-2.0, with telemetry disabled by default and no hosted user-facing service.

    Regulatory applicability¶

    GDPR (EU)¶

    Applicability: Not applicable to v0.2.0rc1. No personal data is collected from users by default. The CLI runs locally and does not transmit identifiable information when telemetry is disabled (the default).

    If a user explicitly enables telemetry via lathe telemetry enable, the allowlisted payload (see docs/privacy.md) is engineered to avoid personal data: build IDs are salted and hashed locally, asset names and paths are excluded, and the only network identifier is the TLS connection metadata at the ingest endpoint. Even so, a salted-hash + IP combination from an EU resident could be argued to be personal data under a strict reading of GDPR Recital 30.

    requires-human: re-assess GDPR applicability when (a) any telemetry ingest endpoint is provisioned, (b) any hosted surface ships, or (c) the project ever knowingly accepts data from EU residents. Counsel must confirm controller/processor split, lawful basis, and data-subject-rights surface before public ingest.

    CCPA / CPRA (California)¶

    Applicability: Not applicable to v0.2.0rc1 for the same reason as GDPR: no personal information is collected by default, and the project does not sell or share consumer data because no consumer data is collected.

    requires-human: re-assess if telemetry ingest goes live or if any hosted surface ships, particularly for "Do Not Sell or Share My Personal Information" surface requirements and the right-to-delete pathway.

    COPPA / child-safety¶

    Applicability: Not applicable to v0.2.0rc1. Lathe is a developer-facing CLI compiler for 3D asset intent. It is not directed at children under 13, does not have an account system, and does not collect personal information.

    Export control (EAR / Wassenaar)¶

    Applicability: Lathe is open-source software made publicly available on GitHub and (when published) PyPI. Publicly available open-source software is generally classified ECCN 5D002 with the TSU (Technology and Software — Unrestricted) license exception under EAR §740.13(e), which permits unrestricted publication.

    requires-human: confirm with counsel before making any public ECCN claim, particularly because Lathe optionally integrates with learned-model providers (Hunyuan3D, VGGT) whose model weights have separate export-control considerations distinct from Lathe's source code.

    Sanctions screening (OFAC / UK / EU)¶

    Applicability: GitHub and PyPI handle sanctions enforcement at the distribution-host layer. Lathe itself does not ship a billing or account-creation surface, so there is no Lathe-side sanctions-screening obligation in v0.2.0rc1.

    requires-human: document the project's position on sanctioned-jurisdiction distribution once counsel weighs in. Re-assess if any hosted surface, paid plan, or contributor-CLA flow ships.

    PCI-DSS¶

    Applicability: Not applicable to v0.2.0rc1. Lathe does not accept, process, store, or transmit payment card data.

    HIPAA¶

    Applicability: Not applicable to v0.2.0rc1. Lathe is not a covered entity or business associate, and does not handle protected health information.

    SOC 2¶

    Applicability: Not applicable to v0.2.0rc1. SOC 2 attests to the controls of a service organization; Lathe does not operate a service in this release. requires-human: re-assess if any hosted surface ships and Lathe becomes a service organization, particularly Trust Services Criteria for Security and Confidentiality.

    Vendors touching user data¶

    Vendor Data handled DPA status Scope Removal target
    (none) — — — —

    PyPI is used for distribution and GitHub is used for source hosting, Actions, and security advisories. Neither is a vendor "touching user data" in the sense relevant here, because Lathe transmits no user data to either service beyond what the user themselves chooses to publish.

    requires-human: re-assess this table when any data-handling vendor (ingest provider, error-reporting service, analytics, hosted CI for end users, etc.) is added.

    DPA status¶

    N/A in v0.2.0rc1 — no vendor touches user data.

    Trigger conditions for needing a Data Processing Agreement:

    • Any third-party telemetry / analytics / error-reporting service is added.
    • Any hosted ingest endpoint operated by a third party is provisioned.
    • Any feature ships that uploads user-authored .lth content, refs, or build artifacts to a third-party system.

    Editor addon license compatibility (Godot)¶

    Godot itself is MIT-licensed. An addon under MIT or Apache-2.0 is compatible both with the addon's host (Godot) and with the Lathe repository.

    The Godot addon ships at editors/godot/lathe-addon/. As of the Phase 2 verification pass on 2026-04-28, an Apache-2.0 LICENSE file has been added at editors/godot/lathe-addon/LICENSE that points to the repo-root LICENSE and reproduces the standard Apache-2.0 boilerplate header. This satisfies the typical Godot AssetLib expectation that an addon directory carries a visible license file independent of the parent repository.

    requires-human: confirm that the Godot AssetLib publication path accepts an Apache-2.0 addon license (vs. a strict MIT preference) before any AssetLib listing is submitted. Recorded as a follow-up in Phase 16 of the readiness task list.

    Blender GPL boundary¶

    Blender is GPLv3 software. Lathe invokes Blender as a separate operating-system subprocess via the topology backend lathe.topology.blender_hard_surface_v1 and the Codex bridge planner (lathe/bridge/blender_plan.py). Lathe does not link Blender code into its own address space, does not redistribute Blender binaries or sources, and does not embed Blender Python modules.

    Reasoning: under widely held interpretations of the GPL (including the FSF's own published guidance on subprocesses with arms-length data exchange), a separate-process invocation across a process boundary, with structured input and output, does not produce a derivative work of the invoked program. On that basis, Lathe's Apache-2.0 license is not affected by Blender's GPL, and Blender remains a user-installed optional dependency rather than a redistributed component.

    requires-human: counsel must concur with this subprocess-boundary reasoning before any "no GPL impact" claim is made publicly. The reasoning above is the maintainer's good-faith engineering judgement and is not legal advice.

    Blender GPL boundary verification¶

    The compliance review's Blender boundary section above relies on Lathe invoking Blender as a separate operating-system subprocess rather than linking Blender Python modules in-process. The Phase 2 verification pass confirmed this concretely:

    • No in-process bpy import in lathe/. A repository-wide grep for import bpy and from bpy over the lathe/ package returned zero matches. Blender's Python module is never imported by the Lathe runtime.
    • Subprocess invocation site. Topology stage code lives in lathe/core/stages/topology.py:19 (import subprocess) and the actual Blender invocation is delegated to lathe.sandbox.blender.run_blender_sandboxed. The sandbox helper itself uses subprocess.run/subprocess.Popen (lathe/subproc.py:204, lathe/subproc.py:225, lathe/subproc.py:247, with the Blender-specific path documented at lathe/sandbox/blender.py:1-103, lathe/sandbox/blender.py:240,272). Invocation happens through a child process with structured input/output (input/output GLB paths plus a separate adapter script under scripts/blender_topology_adapter.py).
    • Codex Blender bridge. The Codex bridge planner (lathe/bridge/blender_plan.py) generates a plan; execution is layered through lathe/blender/execution.py, which also routes through run_blender_sandboxed (lathe/blender/drivers.py:12,47-77). No in-process Blender import.
    • Topology adapter runtime selection. lathe/adapters/blender_subdiv.py contains a single comment at line 73 noting that the Blender subprocess module is imported lazily; this is a reference to the in-tree subprocess helper, not to bpy.

    Conclusion: the subprocess-boundary reasoning in the GPL section above is consistent with the actual code. requires-human: counsel must still concur with this engineering judgement before any public "no GPL impact" claim, but the engineering substrate is verified and not at risk of an in-processbpyimport slipping in unreviewed.
