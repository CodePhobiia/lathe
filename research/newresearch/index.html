    My blunt read: we should not try to make the current “Manifold boolean after every op” pipeline 10× faster as-is. That path will keep punishing us with intermediate mesh copies, topology churn, material loss, and face-count blowups.

    The right architecture is:

    Lathe intent → typed morphology graph → anchor/constraint placement → lazy feature/CSG DAG → batched boolean/arrangement compiler → deferred bevel/sweep/features → zone-preserving mesh → UV/material/LOD compiler → render-based validators.

    Manifold can still be useful, but it should be an execution backend, not the core representation of the asset.

    1. Geometry representation¶

    Best substrate for mid-volume procedural game assets¶

    For our target—hard-surface procedural game props with watertight booleans, semantic parts, materials, bevels, and LODs—the right substrate is a hybrid, not pure CSG, not pure B-rep, and not pure SDF.

    Manifold’s design goal is robust manifold triangle-mesh operations with arbitrary vertex properties/material mapping and guaranteed manifold output, which is valuable for us. But that does not make “one mesh boolean per Lathe op” the right architecture. (manifoldcad.org) CGAL’s Nef polyhedra show the opposite end of the spectrum: mathematically closed boolean representations, but heavier than what we want for fast procedural game assets. (doc.cgal.org) OpenVDB-style CSG is excellent when we can accept level-set resolution and remeshing tradeoffs, but it is not naturally good at crisp CAD-like feature boundaries and material-zone preservation. (openvdb.org)

    Boolean frontier¶

    The frontier is not “which library is fastest?” It is when evaluation happens and how much provenance survives.

    Manifold is the practical default for robust watertight triangle booleans. It breaks down for us when we repeatedly convert meshes, repeatedly materialize intermediate results, and force every feature into final topology too early.

    libigl mesh arrangements are the conceptual model I would study for scaling to many operations: build an arrangement once, classify cells/windings, then extract the result. The libigl variadic boolean interface explicitly supports boolean expressions over multiple meshes through winding-number filters, which is much closer to what we want than serial binary booleans. (alecjacobson.com) Mesh-arrangement work also directly addresses robustness on messy triangle inputs, while noting that many earlier algorithms require overly strict mesh assumptions. (Columbia Computer Science)

    CGAL Nef polyhedra are the robustness reference, not the production-speed target. They are closed under boolean operations and regularization, but the cost and complexity are not aligned with fast game-asset generation. (doc.cgal.org)

    OpenVDB CSG is excellent for many unions/differences and organic effects, especially when exact sharp topology is less important. But transforms, resampling, and grid resolution become architectural concerns. (openvdb.org)

    Learned geometry is not a boolean kernel replacement. It can propose shapes, priors, parameter values, and visual critiques, but I would not trust it as the source of deterministic watertight production topology.

    Kernel architecture for 200 ops per asset¶

    For our case—origin-watertight hard-surface booleans, ~20 ops today, wanting ~200 ops without per-op manifold copies—we need a lazy batched compiler.

    The design:

    1. Keep a lazy CSG/feature DAG.Lathe ops should not immediately become final meshes. They should become typed nodes: box, cylinder, cut, union, inset, bracket, bevel rule, material zone, decal anchor.

    2. Cache primitive tessellations and analytic descriptors.A cylinder primitive should not regenerate or re-enter from_trimesh every time. It should have a stable primitive ID, transform, tessellation policy, and semantic role.

    3. Broadphase spatial clustering.Most ops do not interact. A crate body, four corner guards, handles, hinges, and decal plates can be clustered by bounding boxes. Only overlapping clusters need expensive arrangements.

    4. Evaluate booleans variadically per cluster.Instead of 200 serial binary booleans, compile all interacting meshes in a cluster, build one arrangement, classify by the boolean expression, and extract once. The libigl variadic boolean model is the right mental model here. (alecjacobson.com)

    5. Carry provenance through the kernel.Every output face needs source_part_id, source_face_role, material_class, uv_policy, feature_role, and zone_id. Without that, material zones and validators will always be bolted on too late.

    6. Defer bevels and fillets.Do not bevel primitive edges before booleans unless the bevel is structurally required. Run booleans on simpler forms, then select final edges by semantic/topological rules and apply bevels with a budget.

    7. Do not fuse everything early.Some pieces should remain separate submeshes or instances: bolts, handles, corner brackets, trim strips, hinge barrels. A single watertight fused mesh is sometimes the wrong output for game assets.

    8. Add an optional SDF branch.Use it for dents, chipped paint masks, eroded corners, soft damage—not for every hard-surface feature.

    This lets us scale from “20 expensive mesh operations” to “200 authored feature operations” because most authored ops will not become full topology operations.

    6. Polygon budget¶

    A 1m crate at 125k faces is not a geometry achievement; it is a pipeline smell.

    The waste usually comes from:

    1. Primitive tessellation defaultsCylinders, bevel arcs, spheres, screw heads, and curves are oversegmented.

    2. Serial boolean fragmentationEach cut creates extra triangles and slivers, especially on coplanar or near-coplanar surfaces.

    3. Premature bevelsBeveling before booleans multiplies topology.

    4. Uniform bevel divisionsA tiny internal edge gets the same treatment as a hero silhouette edge.
