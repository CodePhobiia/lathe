# Shape-Stage Blocker Audit

Scope: SHAPE stage and everything upstream — `lathe/asset_graph.py`, `lathe/assembly_kernel.py`, `lathe/scaffold_compiler.py`, `lathe/shape_ir.py`, `lathe/feature_grammar.py`, `lathe/feature_ops/`, `lathe/exact_solids.py`, `lathe/geometry_kernel.py`, `lathe/feature_fusion.py`, `lathe/blueprints/containers.py`, `lathe/primitive_selector.py`, `lathe/asset_quality/{construction_graph,grammar_lowering,shape_ir_v2,family_grammar,highlow_relation,design_brief,diagnostics}.py`, `lathe/shape/backend.py`. Method: end-to-end trace of `examples/brassbound_chest.lth`, plus targeted Grep/Read across the shape stage and `lathe.cli build` of the chest into `tmp_audit_shape/`. Inspected `tmp_audit_shape/brassbound_chest/stages/shape/candidate_00.glb`: 36 044 faces, 17 975 verts, watertight=False — the shape-stage handoff is reasonably dense and the chunky chest in production isn't the shape stage's fault, it's downstream (topology stage drops it). Pipeline-auditor confirms.

## Top Real Blockers (ranked)

### 1. Authored intent has no path into geometry — only ~12 source fields read

**File/line**: `lathe/asset_graph.py:84`, `lathe/assembly_kernel.py:7230`, `lathe/blueprints/containers.py:_chest_blueprint`.

**What's broken**: The `.lth` source declares 11 distinct authoring sub-blocks for the chest (`intent`, `geometry { mode, seam_classes, edge_classes, integration_rules }`, `features { density, allow=[inset_panel, frame_lip, trim_band, clasp_set, recessed_handle, support_bracket, edge_break] }`, `surface { patterns=[plank_spacing_hero, rivet_row_hero] }`, `assembly`, `search`, `repair_policy`, `build.shape { candidates, seed, symmetry, preserve }`). The shape stage **reads almost none of it**. The path is:

1. `asset_graph.py:84` infers family from a 3-token part-name match (`{lid_panel, front_hatch, lock_plate} <= set(parts)`) — chest, drone, vehicle, road, infrastructure each have their own hardcoded token rule.
2. The family routes to `_chest_blueprint` (`blueprints/containers.py:12`) which produces a hardcoded 7-component layout from `scale_cm` plus `±3% rng.uniform` jitter. The author's `scale = 0.8m` is read; nothing else from `intent` or `geometry`.
3. `_component_primitives` (`assembly_kernel.py:7230`) dispatches off `component.component_type` only — `shell→_shell_primitives`, `lid→_lid_primitives`, etc. There is no `feature_grammar` / `family_grammar` / `style_stack` lookup at this seam.
4. `features.allow = [inset_panel, frame_lip, ...]` — the user explicitly enumerates the feature ops. None of those tokens are read in the shape path. `feature_grammar.py:_shape_component_features` (line 101) emits features purely from `component.component_type` + family hardcoded branches (e.g. `if asset_graph.family == "brassbound_chest"` line 143).
5. `geometry.edge_classes = [hero_bevel, support_bevel, trim_edge]` and `geometry.seam_classes = [panel_seam, lid_break, clasp_cut]` are read **once**, only for the chest, by `_apply_chest_edge_class_bevels` (`assembly_kernel.py:8642`). Other families discard them.

**Asset-quality consequence**: Authoring is mostly cosmetic. Editing `features.allow`, `geometry.edge_classes`, `geometry.integration_rules`, `surface.patterns`, `intent.style_target = "stylized_pbr_aaa"` etc. has zero effect on the produced ShapeIR because none of those fields reach the kernel. The chest you get is the chest the kernel hardcodes — only the scale and rng-jitter range are author-controllable.

**Fix sketch (modular)**: Introduce a `ShapeAuthoringContext` dataclass populated from the resolved AST in `asset_graph.py` that exposes `feature_allowlist`, `seam_classes`, `edge_classes`, `integration_rules`, `style_target`, `density`, `preserve_set` as plain typed fields. Thread it through `compile_assembly_blueprint(asset_graph, blueprint, *, context)`, `_component_primitives`, `_shape_component_features`. Replace `if asset_graph.family == "brassbound_chest"` with `if "edge_break" in context.feature_allowlist` etc. **Effort: M** (touches 5 files; ~300 LOC delta; deterministic).

### 2. ShapeIR v2 / grammar_lowering / construction_graph are dead-end validators, not authoring layers

**File/line**: `lathe/asset_quality/shape_ir_v2.py:1-58`, `grammar_lowering.py:1-49`, `construction_graph.py:39-53`. `lathe/scaffold_compiler.py` does **not** import any of the three (`grep -n "grammar_lowering|shape_ir_v2|construction_graph" lathe/assembly_kernel.py lathe/scaffold_compiler.py` returns no matches).

**What's broken**: ShapeIR v2 introduces seven semantic op families (SOLID_OPS, BOOLEAN_OPS, EDGE_OPS, SOP_OPS, REPETITION_OPS, INTEGRATION_OPS, WEAR_OPS). `construction_graph` introduces 15 node-types and 10 edge-types (`inset_into`, `wraps_around`, `cuts`, `mirrors`, `aligned_with`). `grammar_lowering` has hardcoded canonical dimensions per family. **All three are wired into `lathe/core/stages/validate.py` as `weight=0.0` informational validators that run after the shape stage has already produced its mesh.** They synthesize interesting JSON trees that nothing reads: `runtime["grammar_lowering"]["synthesized_graph_nodes"]` is built and feeds back into … the family_grammar validator's coverage report. The assembly kernel has no awareness of any of them.

**Asset-quality consequence**: Three full Phase 4/5/6 layers built on the premise of richer authored geometry — and the geometry itself doesn't see them. Bevels are still chest-hardcoded constants in `assembly_kernel.py:8379`; the `op.inset` family in v2 with corner_radius/depth/width parameters cannot affect mesh output; the `wraps_around` / `cuts` edge semantics in the construction graph cannot drive boolean topology. This is the single biggest hidden capability in the codebase.

**Fix sketch (modular)**: The asset graph builder should call `grammar_lowering.lower(design_brief, parts, construction_graph_nodes)` first to produce a `ShapeProgram` (sequence of `ShapeOp`s). The assembly kernel should consume `ShapeProgram` *before* the family-specific blueprint factory — i.e., the ShapeProgram becomes the source of truth for solid creation and modifier records, and `_chest_blueprint` becomes a fallback for assets without an explicit ShapeProgram. The existing `solid_ir_from_shape` (`geometry_kernel.py:490`) already shows the right shape — invert the direction. **Effort: L** (this is the architectural change Phase 7+ alludes to in the docstrings, ~800 LOC; needs careful staging).

### 3. CSG is hardcoded "off" for non-hero families — `enabled=False` at `feature_fusion.py:40`

**File/line**: `lathe/feature_fusion.py:25-48`.

**What's broken**: `integration_config_for_family` returns `{"enabled": hero_family, ...}` where `hero_family` is membership in a **frozen 8-name set**: `{brassbound_chest, industrial_crate, mechanical_door, console_terminal, service_cabinet, control_pedestal, supply_container, hero_sword}`. For every other family, `fuse_shape_ir` (`geometry_kernel.py:745`) returns `(None, "constructive_fallback")` and `_runtime_from_shape_ir` (`scaffold_compiler.py:515`) falls through to `trimesh.util.concatenate(meshes)` — meshes are *appended*, not unioned. So a `procedural_vehicle`, `procedural_setpiece`, `weapon`, `tool`, `creature`, `furniture`, `utility_pole`, etc. — every non-hero asset — emits intersecting mesh fragments with no fused topology, no seam edges, no bevels. The audit-pipeline-auditor's chunky-sliver-triangle observation downstream is amplified for all non-hero assets.

**Asset-quality consequence**: Lathe is officially modular for "anything", but **CSG only exists for 8 specific names**. A new asset declared `family = "lantern"` produces a literal pile of overlapping primitives.

**Fix sketch (modular)**: Replace the family allowlist with a per-asset capability check: enable CSG when (a) `intent.asset_class in {hero, prop, weapon, tool}` OR (b) authoring declares `geometry.integration_rules` with a boolean op (which the chest already does: `[boolean_union, preserve_lid_break]`), OR (c) `build.shape.mode in {generate, assemble, adapt}`. Pitch / blur_sigma should derive from `fidelity.tier`, not family. `exact_mode = "component_assembly"` should be triggered by an authored declaration like `geometry.integration_rules = [no_csg]` instead of the hardcoded `if family in {console_terminal, control_pedestal, service_cabinet}` set. **Effort: S** (~50 LOC, single file).

### 4. Manifold CSG kernel is available but only invoked as a *fallback*

**File/line**: `lathe/scaffold_compiler.py:453-475`, `lathe/geometry/kernel.py:32`, `lathe/scaffold_compiler.py:154-260`.

**What's broken**: `manifold_available()` returns `True` on this machine. `MANIFOLD_KERNEL_ID = "lathe.geometry.manifold_v1"` is the registered default. But `_fuse_via_manifold_kernel` (line 154) is only entered when `fused_mesh_ir is None and geometry_kernel_id == "lathe.geometry.manifold_v1"` — i.e., **only after `fuse_shape_ir` already failed**. The default path is the SDF-voxel path or the trimesh exact-solids path (`exact_solids.py:1864` `_combine_explicit_meshes` using `trimesh.boolean.union/difference`), which has historically been brittle (its own `BOOLEAN_EXCEPTIONS` fallback at line 1916 catches a long list of failure modes and silently degrades to `trimesh.util.concatenate`). Manifold is the more robust modern CSG kernel and would handle most ops cleanly — but it never runs when the trimesh path returns *anything*, even garbage. Worse: `_fuse_via_manifold_kernel` itself bails (returns `None`) for any primitive type other than `box/cylinder/revolved_profile/extruded_profile/torus/subdivision_box/swept_profile` — `lofted_solid` is missing (line 234 `else: return None`), and lofted_solid is the chest body's primary primitive.

**Asset-quality consequence**: Lathe ships with a robust CSG kernel and never uses it as the primary path. Booleans are brittle; failures silently produce concatenated overlapping meshes; the modular ShapeIR vocabulary is partially routed (lofted_solid → can't go through manifold).

**Fix sketch (modular)**: (a) Make Manifold the *primary* CSG kernel for `exact_mode in {explicit_mesh, boolean_*}` paths — re-order `scaffold_compiler.py:_runtime_from_shape_ir` so manifold is tried first when it's the resolved kernel, with the trimesh boolean as the fallback. (b) Add lofted_solid to `_fuse_via_manifold_kernel`'s primitive switch by triangulating section-rings into manifold meshes (the `exact_solids._lofted_solid_mesh` already produces tris; just need the manifold ingress wrapper). **Effort: S** for ordering, **M** for full primitive coverage.

### 5. Density is set by a 3-tier integer ladder (2/4/6 features per component), not by author intent

**File/line**: `lathe/feature_grammar.py:112`.

**What's broken**: `feature_count = 2 if blockout else 4 if game else 6 if hero`. Hard cap. The chest declares `features.density = hero` and `build.topology.target_quads = 12000`. That maps to `feature_count = 6`, plus a couple of `density >= 1.0` or `density >= HIGH_FEATURE_DENSITY` gates that emit small extra batches. The author cannot ask for "30 fasteners in a row" or "rivet pattern of 12×4". The `params.feature_density` knob is lower-bounded at 0.6 (`density = max(0.6, params.feature_density)`) — the author cannot dial features *down* either. The `brass_band_rivets_features` call in the chest branch hardcodes `band_count=3, rivets_per_band=8` (line 148-156). Density is fundamentally not author-controllable.

**Asset-quality consequence**: All hero assets look like they have the same number of fasteners / panels / ribs — because they do. The visual sense of "this asset has a *lot* of detail" or "this is a sparse minimalist prop" is not expressible.

**Fix sketch (modular)**: The `features` block in `.lth` should accept `density: 1.6` as a multiplier and a `repetition_pattern` reference to a `pattern` in the surface stdlib. `feature_count` becomes `int(round(base * density_multiplier))`. ShapeIR v2's `REPETITION_OPS` (`shape_ir_v2.py:30`) already enumerate `repeat_grid`, `repeat_along`, `repeat_radial`, `mirror`, `instance_along` — the IR exists, it's just not consumed. **Effort: S** for `feature_count` scaling, **M** if you wire REPETITION_OPS through.

### 6. The primitive selector is a 1100-line per-family token soup

**File/line**: `lathe/primitive_selector.py:225-373`, `lathe/assembly_kernel.py:7275-7773`.

**What's broken**: `primitive_selector.py` defines per-family selector blocks with hand-curated component-name sets and tag sets — `_CHEST_VOLUME_COMPONENTS`, `_CHEST_PANEL_COMPONENTS`, `_CHEST_PANEL_TAGS`, then again `_DRONE_VOLUME_COMPONENTS / _DRONE_PANEL_COMPONENTS / _DRONE_LATHED_COMPONENTS / _DRONE_SWEPT_COMPONENTS`, then again for door, console, cabinet, pedestal, wall_panel — **seven full mini-DSLs, each ~30-50 lines, and `_select_replacement` (line 546) is 200 lines of nested if-blocks dispatching by family-context THEN component_type THEN tag-set**. The same pattern repeats in `assembly_kernel.py:7275-7773`'s `_component_type_from_source` and `_component_types_from_source` aliases dictionary (~500 lines of token tuples).

**Asset-quality consequence**: To add a *new* hero family the maintainer must (a) add a token rule to `asset_graph.py:_infer_family`, (b) add a blueprint factory in `blueprints/`, (c) add 4 new constant sets in `primitive_selector.py`, (d) add a context-detector function `_is_lantern_selector_context`, (e) add a 20-line dispatch block in `_select_replacement`, (f) add the family to `_HERO_FAMILIES` in `feature_fusion.py`, `highlow_relation.py`, `surface_runtime.py`, and (g) add bevel constants in `assembly_kernel.py`. Seven file edits per new family. This is the antithesis of "anything should be possible" — the chest fixture has effectively become the hardcoded type-system.

**Fix sketch (modular)**: Replace per-family selector blocks with a tag-driven selector. The author or family stdlib declares `selector_rules = [(tag_set, primitive_recipe), ...]` and the selector becomes a generic 100-line dispatcher. The seven `_is_X_selector_context` functions collapse to one `_match_selector_context(style, rules)` and the 200-line `_select_replacement` becomes a deterministic priority-ordered match. **Effort: M** (~600 LOC reduction; 200 LOC of tag-rule data moves to YAML/JSON in `std/`).

### 7. CSG seams are ATTEMPTED but the bevel only runs on hero-set families

**File/line**: `lathe/exact_solids.py:1904-1915`, `assembly_kernel.py:8642`.

**What's broken**: The `boolean → seam → bevel` chain is real: `_extract_post_boolean_seam_groups` runs after the boolean union/difference, and `_apply_post_boolean_polybevel` consumes the seam groups (`exact_solids.py:1910`). **But** seam groups are populated by `boolean_seam_groups` declarations on the source primitives, and **only `_apply_chest_edge_class_bevels` populates those**, and only when `asset_graph.family == "brassbound_chest"`. For every non-chest family, primitives have empty `boolean_seam_groups`/`bevel_seam_groups` lists, so post-boolean polybevel records *no* targets — meaning Phase-1's "boolean → bevel(seam_group)" actually produces visible bevels **for the chest only**.

**Asset-quality consequence**: All non-chest hero families that go through `exact_mode=explicit_mesh` get fused topology with raw boolean edges and no edge bevels — silhouettes are technically correct but read as "CAD output", not "stylized PBR AAA". The chest looks better than its peers because of one hardcoded function.

**Fix sketch (modular)**: Generalize `_apply_chest_edge_class_bevels` to `_apply_edge_class_bevels(primitives, edge_classes, seam_classes, *, mapping)` where `mapping` defaults to a global `_EDGE_CLASS_BEVELS` dict and can be overridden per-family from `std/families/<name>/edge_bevels.yaml`. Drop the family-equality gate at `assembly_kernel.py:8642` — fire it whenever `geometry.edge_classes` is authored. **Effort: S** (~80 LOC).

### 8. `_chest_brass_band_primitives` reads body extents from a hardcoded component-type guess

**File/line**: `lathe/assembly_kernel.py:8503-8526`.

**What's broken**: To find "the body to wrap brass bands around" the function does `for component in blueprint.components: if component.component_type in {"shell", "body"}: body = component; break`. If the family happens to call its primary volume `chassis` or `hull` or `monolith`, no bands are emitted. The function produces bands at `band_offsets = (-0.78, 0.0, 0.78)` — three hardcoded heights regardless of body proportion. The torus minor radius is `min(height * 0.04, 1.2)`. None of this is parameterized from `surface.patterns = [plank_spacing_hero, rivet_row_hero]` (`brassbound_chest.lth:81`).

**Asset-quality consequence**: Asset modularity smell — feature emitters are coupled to fixture-specific primitive layouts. A "barrel" or a "lantern" cannot reuse the band feature without wearing the chest fixture's geometry assumptions.

**Fix sketch (modular)**: Move band emission into a generic `feature_op` — `band_wrap` — registered in `feature_ops/` (currently mostly empty: `__init__.py` is the only file there). The op consumes a target component (selected by tag, not type), a band count, a band placement function, and an axis. The chest authors `surface.patterns = [{op: band_wrap, target: tag(body), count: 3, axis: y, placement: linspace(-0.78, 0.78, 3)}]`. **Effort: M** (~200 LOC; opens up a real feature-op registry).

### 9. The ShapeIR vocabulary is reachable but not authored from `.lth`

**File/line**: `lathe/shape_ir.py:14-180` (defines all primitives), `lathe/parser/grammar.py` + `grammar/lathe.lark` (no primitive-mention from authoring).

**What's broken**: ShapeIR supports `box, cylinder, sphere, revolved_profile, extruded_profile, torus, subdivision_box, swept_profile, lofted_solid, heightfield`. The `heightfield` primitive is documented for terrain (`shape_ir.py:67`) and fully implemented in `exact_solids.py:_heightfield_mesh`. **But authors cannot reference any of these from `.lth`**: the grammar has no `solid` / `primitive` / `lofted` / `revolve` keywords. The only way an author influences which primitive gets used is indirect — token names like `lid_panel` flow through `infer_family → _chest_blueprint → _component_primitives → _lid_primitives → _lofted_solid`. There is no `.lth` syntax for "this part is a torus with major=15 cm, minor=2 cm" or "this part is a revolved profile from points [...]". This means assets the kernel doesn't already know cannot use the rich vocabulary at all.

**Asset-quality consequence**: The richer-vocabulary work was completed at the IR level (good!) but the authoring surface is the same `intent { parts = [body, lid] }` it was 6 commits ago. New asset families have to implement a new blueprint factory in Python; they can't be authored in `.lth`.

**Fix sketch (modular)**: Add a `primitives { ... }` block to the grammar and resolver that accepts low-level ShapeIR-equivalent declarations (`primitive { type: torus, part: trim_band, center: (0, 5, 0), major_radius: 18cm, minor_radius: 0.4cm }`). Source primitives flow into `compile_assembly_blueprint` alongside blueprint-derived ones (the `_authored_source_components` pathway at `assembly_kernel.py:8615` exists for components but not primitives). **Effort: M** (grammar + parser + resolver + checker; ~400 LOC across 4 files).

### 10. Boolean fallback silently swallows CSG failures and emits concatenated meshes

**File/line**: `lathe/exact_solids.py:1916-1918`.

**What's broken**: `except BOOLEAN_EXCEPTIONS as exc: combined = trimesh.util.concatenate(meshes)`. The exception class list is (line 18) `(ValueError, RuntimeError, AttributeError, IndexError, OSError)` — a wide net. When trimesh's CSG fails for *any* reason, the build proceeds with overlapping meshes and a `boolean_fallback_reason` recorded into the integration report. There is no diagnostic surfaced to the validate stage that flags "this asset's booleans never converged" — only the textual reason in the report.

**Asset-quality consequence**: Silent quality regressions. A small ShapeIR change can flip an asset from "fused with seams" to "concatenated with no seams" without any user-visible signal except a slightly worse score downstream.

**Fix sketch (modular)**: Emit a `quality_diagnostics` entry with code `L0721 boolean_csg_fallback` whenever `boolean_fallback_reason` is set, with severity `error` for hero families and `warning` otherwise. Hard-fail the validate stage at threshold when CSG silently fell back for a hero asset. **Effort: S** (~30 LOC).

## End-to-end Trace: brassbound_chest.lth → mesh

1. `examples/brassbound_chest.lth:45-65` declares `intent`. The author asks for `"ornate brassbound loot chest"`, `style_target="stylized_pbr_aaa"`, `parts=[body, lid_panel, front_hatch, lock_plate, handle_l, handle_r, foot_l, foot_r]`, `materials=[oak_planks, brass_bands, red_velvet_lining]`.
2. `examples/brassbound_chest.lth:67-92` declares 4 more authoring blocks — `geometry { mode=exact_hard_surface, seam_classes=[...], edge_classes=[...] }`, `features { density=hero, allow=[...] }`, `surface { patterns=[plank_spacing_hero, rivet_row_hero] }`, `assembly { components=[...] }`. **Of these, only `geometry.edge_classes`, `geometry.seam_classes`, and `assembly.components`'s presence reach the kernel.** The `intent.style_target`, `features.allow`, `surface.patterns`, `assembly.components` content, `geometry.integration_rules`, `intent.materials` are all authoring noise as far as ShapeIR is concerned. **Loss: ~85%.**
3. `parser → normalizer → resolver → asset_graph.build_asset_graph(asset)`. `asset_graph.py:84` matches `{lid_panel, front_hatch, lock_plate} <= set(parts) → family = "brassbound_chest"`.
4. `scaffold_compiler.compile_scaffold_candidates`. `resolve_blueprint(asset_graph, ..., index=0)` returns `_chest_blueprint(asset_graph, rng, 0)` — a 7-component layout with width/height/depth derived from `scale_cm=80` and `±3% rng.uniform`. **The author's `intent.role` and `intent.style_target` are not consulted.**
5. `compile_assembly_blueprint(asset_graph, blueprint)`. For each component, `_component_primitives` dispatches by `component_type`: `shell→_shell_primitives` (lofted body+liner), `lid→_lid_primitives` (5-section dome), `frame→_frame_primitives`, `door→_door_primitives`, `lock_plate→_panel_primitives`, `handle→_handle_primitives` (swept_profile), `foot→_foot_primitives` (revolved_profile lathed leg). After component dispatch, `_chest_brass_band_primitives` adds 3 toruses, and `_apply_chest_edge_class_bevels` tags primitives with `v2_polybevel_modifier`. **This is the only place chest's authored `geometry.edge_classes` is honored. The line is `if asset_graph.family == "brassbound_chest"` — surrounded by hardcoded chest constants.**
6. `compile_feature_enhancements` → `_shape_component_features`. Adds 6 more features per `shell/body` component (`feature_count=6` for hero), all based on `component_type`, plus a hardcoded `if asset_graph.family == "brassbound_chest" and "plank_displacement" in component.tags` branch (`feature_grammar.py:143`) that emits the 24 brass-band rivets.
7. ShapeIR is now ~30 primitives (8 components × ~2 primitives each + 3 brass bands + 24 rivets). **The user's `features.allow = [inset_panel, frame_lip, trim_band, ...]` was never read. Whatever subset of those features ends up emitted is determined entirely by `component_type`.**
8. `fuse_shape_ir(shape_ir, fidelity)` → `integration_config_for_family("brassbound_chest", hero) → enabled=True, exact_mode=explicit_mesh` → `_compile_exact_mesh_ir → compile_explicit_surface_mesh → _combine_explicit_meshes(combine_mode="explicit_mesh")` → `_boolean_union(...)` then `_boolean_difference(...)` (`exact_solids.py:1891-1895`) using `trimesh.boolean`. Manifold kernel is *not* used (it's only the fallback when this fails).
9. Post-boolean `_extract_post_boolean_seam_groups` + `_apply_post_boolean_polybevel`. Seam groups are populated **because** step 5 tagged primitives with `boolean_seam_groups = [{name: panel_seam}, ...]` from `_chest_edge_class_bevels`. The post-boolean polybevel produces actual bevel geometry. ✓
10. The candidate mesh is the chest GLB I inspected: 36 044 faces, 17 975 verts, watertight=False. The downstream topology stage then collapses it to the audited 286 quads — that's a topology-stage problem, not a shape-stage problem. (Pipeline-auditor is correct.)

**Where richness collapses**: Steps 1→2 (authoring → graph) and 2→4 (family-routing). 85% of authored intent is dropped before the asset graph is even built. The remaining 15% (`scale`, `parts`, `family-via-tokens`, `geometry.edge_classes for chest only`) is what produces the chest you actually see.

## Modularity Smells

- **`assembly_kernel.py:341-357 _is_container_component`** — uses a hardcoded tag set `{"container","chest","brassbound","loot","wood_and_brass","crate"}` that gates the `_shell_primitives` and `_lid_primitives` lofted-solid path. New "container-shaped" assets must add their tags here.
- **`assembly_kernel.py:8400-8402`** — three constant component-type sets `_CHEST_HERO_COMPONENTS`, `_CHEST_SUPPORT_COMPONENTS`, `_CHEST_TRIM_COMPONENTS` map component types to bevel classes. Implicit in the chest fixture's component layout.
- **`assembly_kernel.py:8642`** — `if asset_graph.family == "brassbound_chest":` gates two ~150-LOC code paths (band emission + edge-class bevel tagging) that should be tag-driven.
- **`feature_grammar.py:143`** — `if asset_graph.family == "brassbound_chest" and "plank_displacement" in component.tags:` gates the brass-band rivet emission. The whole branch is chest-specific.
- **`feature_grammar.py:134`, `:202`** — `if asset_graph.family == "console_terminal"` gates rib emission and trim band emission. Same anti-pattern as chest.
- **`feature_fusion.py:25-34`** — `_HERO_FAMILIES` frozen-set hardcoded. Repeated in `highlow_relation.py:105-116` and (per pipeline-auditor) in `surface_runtime.py`.
- **`primitive_selector.py:225-373`** — seven per-family `_X_VOLUME_COMPONENTS / _X_PANEL_COMPONENTS / _X_*_TAGS` set-literals. ~150 lines per family.
- **`primitive_selector.py:546-735 _select_replacement`** — 200-line if-cascade dispatching by family-context first, then component_type, then tag-set. The skeleton shape is the same per family; only constants differ.
- **`asset_graph.py:84`** — `{"chest","loot"} & tokens or {"lid_panel","front_hatch","lock_plate"} <= set(parts)` is the chest's family-detection rule. Repeats for ~15 families with bespoke token sets at lines 86-300.
- **`assembly_kernel.py:7275-7773`** — `_component_type_from_source` and `_component_types_from_source` define ~500 lines of token-alias tables for every domain (city, world, harbor, weapon, machine, robot, portal, social, security, research, medical, communication, fashion, media, domestic, ...). This is "anything is possible if I add 8 lines per concept", not "anything is possible".

The single common smell across all the above: **the kernel encodes the schema for richness**, which means new asset shape requires Python edits in many files. The author cannot ship a new family in pure `.lth`.

## Hidden Capability (real code, never reached)

1. **Manifold CSG kernel** (`lathe/geometry/manifold_kernel.py`) — robust, modern, available on the dev box (`manifold_available()→True`), registered as the default kernel ID, **but only invoked as a fallback** behind the trimesh path. Re-ordering the `scaffold_compiler.py:_runtime_from_shape_ir` to try manifold first when `geometry_kernel_id == "lathe.geometry.manifold_v1"` would make CSG dramatically more reliable. Add lofted_solid coverage (currently the manifold path returns `None` for it) and the chest's body fuses through the modern kernel.
2. **`heightfield` primitive** (`shape_ir.py:67-77`, `exact_solids.py:_heightfield_mesh`) — fully implemented terrain primitive with hydraulic-erosion-ready slope/flow/deposition output, **never authored from `.lth`**. The grammar has no primitive-block syntax, and no family-blueprint emits heightfields. A `terrain` asset family with `geometry.mode = heightfield` would unlock procedural terrain immediately.
3. **`lofted_solid` primitive's manifold path** — exists in trimesh exact_solids but is missing from `_fuse_via_manifold_kernel` (`scaffold_compiler.py:234`). 30 LOC to add.
4. **ShapeIR v2 + grammar_lowering** — Phase 5/6 IR is a dormant authoring layer (see Blocker #2). The op vocabulary covers most authored intent (boolean, edge, repetition, integration, wear). Wiring it as the source-of-truth in `compile_assembly_blueprint` would make 85% of the dropped authoring fields meaningful. The construction graph already infers `attached_to`, `mirrors`, etc. from parts — promote it to drive ShapeIR construction.
5. **`feature_ops/` package** — `__init__.py` is the only file (2546 LOC, but in `__init__`, awkwardly). The directory was clearly built as a future home for individual feature operators — `band_wrap`, `inset_panel`, `frame_lip`, `clasp_set` should each be a module here, registered in a deterministic dispatch table keyed on the author's `features.allow = [...]` tokens.
6. **`creative_grammar` / `style_stack` axes** — `scaffold_compiler.py:55-80 _apply_construction_grammar_routing` reads `style_stack.construction_grammar in {free_form, snap_grid, brick_snap, modular_kit}` and routes conditioning. A repair operator that reads "this primitive_selector reason was X but visual_quality scored low" could close the autonomous-loop gap.

## Calibration Questions

1. **Should authored `features.allow = [...]` be the source of truth, or hint?** If source-of-truth, the kernel becomes a deterministic feature-op dispatcher and the hardcoded `if family == "chest"` branches in `feature_grammar.py:_shape_component_features` go away. If hint, the kernel can override but should record the override in the audit trail.
2. **Do we accept ShapeIR v2 as the new authoring center?** Promoting it from validator to driver is a Phase-7+ effort (~800 LOC). The alternative is to give up on the v2 layer and clean up the dead code in `asset_quality/`.
3. **Is `geometry.mode` real syntax or vestigial?** The author writes `mode = exact_hard_surface` / `mode = generate`. The kernel reads `mode` exactly once in `shape/backend.py:66` and only uses it for the self-reliance gate. If `mode` is meant to switch between hard-surface, organic, terrain, mechanical, etc. authoring grammars, it should drive primitive-vocabulary selection — not just provider routing.
4. **Manifold-first or trimesh-first for CSG?** Manifold is more robust but has a smaller primitive coverage in our adapter. Trimesh's CSG path silently degrades. The current "fallback to manifold" ordering means we get the worst of both. Either backfill the manifold adapter to cover all 10 ShapeIR primitives (M), or accept that manifold is only useful when trimesh fails (S, current state).
5. **What's the bar for "feature density is author-controllable"?** The chest declares `density = hero` and gets 6 features per body. If the author writes `density = 1.6 × hero` should they get 10? If yes, the integer ladder in `feature_grammar.py:112` becomes a multiplier. If the answer is "no, density is fixed per tier", we should rename the field to `tier`.
6. **Is the `family` enum closed or open?** Closed → adding `family = "lantern"` can never produce good output without Python edits. Open → the `family_grammar.py` rules + ShapeIR v2 program have to compose deterministically. We're paying the cost of "open" (every grammar/checker/resolver knows about families) without getting the benefit (an unknown family doesn't produce anything new).
