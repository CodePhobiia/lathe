    Lathe Northstar Full Implementation Plan¶

    Date: 2026-05-11 (revision iteration 1: same day) Status: Canonical end-to-end sequencing plan for completing docs/asset-quality/lathe-implementation-northstar.md in full Scope: All 10 lanes (A-J), all 13 blockers (B0-B12), all 5 phases, plus the procedural synthesizer (procedural-synthesizer-architecture-spec.md, v2) that resolves B12 and unblocks Lanes B/C/I Companion docs: lathe-implementation-northstar.md (intent), lathe-implementation-northstar-current-audit.md (current state), procedural-synthesizer-architecture-spec.md v2 (one architectural slice)

    Revision History¶

    • 2026-05-11 v1 (initial) — first draft. Allowed Cycle 1 to ship stub-only generators and a synthesizer that returns empty programs for unknown families. Treated "one FamilyKnowledge pack per family" as the end-state modular unit. Cycle 3 decommission acceptance used the weak grep 'family ==' lathe/ check. Cycle 6 deferred the domain extension API to Phase 3 work. Recipe count cited as 73; actual is 71. Section 3 / Section 12 disagreed on whether Cycles 1-2 are parallel.
    • 2026-05-11 v2 (this revision) — review iteration resolved six findings:
    • Cycle 1 ships real procedural output. No stub generators. No empty-program route. Per spec v2 §9.3, the first commit produces a non-empty ShapeProgram for authored-intent-only fixtures.
    • The modular unit is policy/style/domain, not family. Plan updated to reflect the spec v2 split into CompositionPolicy, StyleKnowledge, FamilyAlias, DomainExtension. Family aliases SELECT packs; they do not DEFINE structure.
    • no_family_dispatch lint/test replaces the weak grep. Catches _RECIPES.get(family), .get(family) in synthesis/ geometry paths, family in checks, and _FAMILY_* behavior maps. Lives in CI; runs every commit.
    • Recipe decommission interleaves with visual proof. A family migrates only after both the ShapeProgram diff AND a visible build artifact pass. Cycle 3 does not "complete" before Cycle 4 has caught up family-by-family.
    • Domain extension API lands in Cycle 1, not Cycle 6. The DomainExtensionManifest and per-domain registration contract are first-commit deliverables. Cycle 6 becomes "register domain extensions," not "design the extension contract."
    • Recipe count uses the live registry, not a hardcoded number. Plan refers to "the current _RECIPES registry" or a generated audit count. Today: 71 entries. Plus the sequencing contradiction is resolved: Cycle 1 must complete before Cycle 2 can run (Cycle 2 depends on the synthesizer's typed-attribute schemas and generator manifests). Cycles 2 and 3 can overlap. Cycle 3 cannot complete before Cycle 4 has caught up.

    This document is the master plan. The northstar declares what; this declares when and in what order. Each cycle ships production-grade work — no MVPs, no scaffolding-labelled-as-shipping, no demo assets masquerading as proof. Verification per cycle is the floor under "this works," not ceremony.

    0. How This Plan Is Used¶

    Read this when:

    1. Picking up a new session and deciding what to do next.
    2. Sequencing work across multiple agents/sessions.
    3. Tracking northstar completion progress.
    4. Resolving "should we do X next or Y" questions.
    5. Reporting status to stakeholders.

    The plan is laid out as eight cycles of work. Each cycle:

    • Has a stable goal (a sentence the user could state).
    • Names the lane(s) and blocker(s) it advances.
    • Lists concrete deliverables (files, modules, or capabilities).
    • Specifies acceptance criteria (what production-grade looks like).
    • Identifies dependencies on prior cycles.
    • Bounds effort in sessions (1 session ≈ 2-6 focused hours).

    Cycles 1-3 are the procedural-engine foundation. Cycles 4-5 close the imagination-to-life visible loop. Cycles 6-8 are domain expansion, animation vocabulary, and engine integration.

    2. Operating Principles (Inherited From Northstar §5)¶

    Every cycle must respect:

    • Public .lth source compatibility.
    • Stable lathe.shape.intent_mesh_handoff_v1 contract.
    • Public language surface around profile, contract, critic, asset, variant, build-stage names.
    • Attempted-vs-actual tracing for providers, kernels, renderers, topology adapters, UV adapters, package exporters.
    • No expansion of public syntax before the internal execution path proves visible output.
    • No fake evidence of any kind.
    • No chest-only or family-only logic. Generalize via tags, component roles, asset class, operations, or stdlib data.
    • No validators rewarding metadata completeness over visible quality.
    • No "production-ready" or "game-ready" claims unless evidence was generated and checked.

    Production-grade per cycle means:

    • The code is the real thing, not a scaffold.
    • The verification floor (targeted unit tests + at least one full build path where applicable) is green at session end.
    • The output is committed and pushed.
    • The honest claim vocabulary (real | proxy | fallback | unsupported | not verified | blocked) governs every report field.

    Sequencing rules (resolved in v2):

    • Cycle 1 must complete before Cycle 2 starts. Cycle 2 depends on the typed attribute schemas, generator capability manifests, and domain extension manifest that Cycle 1 produces. There is no parallel start.
    • Cycles 2 and 3 may overlap. Cycle 2 (kernel capability) and Cycle 3 (recipe decommissioning) operate on orthogonal layers once Cycle 1's substrate is in place.
    • Cycle 3 cannot complete before Cycle 4 has caught up family by family. A migrated family is only "done" after it has both passed the ShapeProgram equivalence diff (Cycle 3) AND passed the visible-artifact build inspection (Cycle 4). This prevents the failure mode "ShapeProgram diff was acceptable but rendered output is worse."
    • Cycles 4 and 5 are paired and ship in tightly alternating commits. Each Cycle 4 visible-layer slice gets its Cycle 5 diagnostic immediately after.
    • Cycles 6, 7, 8 are strictly gated by their predecessors and do not parallelize backward.

    4. Cycle 1: Procedural Engine Foundation¶

    4.1 Goal¶

    Replace family-name dispatch in grammar_lowering.py with a production-grade procedural compiler pipeline. The substrate must be modular by policy, style, and domain — not by family. Family identity collapses to an alias that selects packs; family identity does not select code paths and does not select structural decisions. Every generator, decorator, knowledge pack, and domain extension is introduced via a stable plugin contract Cycle 1 itself defines.

    No stubs. No empty-returning generators. No no-op routing. Every file committed in Cycle 1 produces real output end-to-end.

    4.2 Lanes And Blockers Advanced¶

    • Lane B (ShapeIR v2 As Drivers) — primary
    • Lane C (Feature Ops And Modularity) — substrate
    • Lane I (Authoring Surface And Stdlib Modularity) — substrate
    • B12 (Chest-Specific Code Is A Product Smell) — core resolution
    • B1 (Authored Intent Dies Before Geometry) — partial resolution

    4.3 Concrete Deliverables¶

    Per procedural-synthesizer-architecture-spec.md v2 §5 and §12. Every file listed here must be production code on first commit — no skeletons, no stubs, no "filled in later" placeholders.

    4.3.3 DomainExtensionManifest contract (new in v2)¶

    The plugin contract for Cycle 6's per-domain packs lands NOW so domains plug in without redesigning the synthesizer:

    @dataclass(frozen=True)
class DomainExtensionManifest:
    """Declares a domain's contribution to the synthesizer.

    Loaded at import time by domain extension packages. The registry
    refuses to register a domain whose manifest reports incomplete
    coverage of its own NODE_TYPES.
    """

    domain_id: str                                     # "hard_surface", "vegetation", ...
    node_type_schemas: Mapping[str, type]              # NODE_TYPE -> typed schema class
    edge_type_schemas: Mapping[str, type]              # EDGE_TYPE -> typed schema class
    generators: tuple[NodeTypeGenerator, ...]
    decorators: tuple[EdgeTypeDecorator, ...]
    required_kernel_capabilities: tuple[str, ...]
    emitted_shape_ir_ops: tuple[str, ...]              # subset of ALL_OPS
    style_pack_compatibility: tuple[str, ...]          # which style packs work
    policy_pack_compatibility: tuple[str, ...]         # which policies apply

    Hard-surface domain is the first DomainExtension registered. Phase 3 domains (vegetation, terrain, WFC, CGA, etc.) become additional DomainExtensions in Cycle 6 — no engine code changes needed at that point.

    4.3.4 Routing change in grammar_lowering.py¶

    def evaluate_grammar_lowering(asset, runtime):
    family = _resolve_family(brief)
    if family in _MIGRATED_TO_SYNTHESIZER:
        return synthesize_shape_program(asset, runtime)
    recipe = _RECIPES.get(family)
    if recipe is None:
        # Unknown families route to the synthesizer, which produces
        # REAL output from the construction graph + brief, NOT an
        # empty program. This is the Cycle 1 acceptance fixture path.
        return synthesize_shape_program(asset, runtime)
    return recipe(brief, parts, graph_nodes)

    _MIGRATED_TO_SYNTHESIZER is initialized in Cycle 1 with the alias authored in §4.3.2 (whichever simple family Cycle 3 picks as its first migration target). Cycle 3 grows that set.

    The test_no_family_dispatch.py contract test is a Cycle 1 deliverable. It scans the codebase and fails if any of these patterns appear in synthesis/geometry/surface paths:

    • _RECIPES.get(family) or _RECIPES[family]
    • Any dict.get(family) or dict[family] where the dict is a _FAMILY_* or _GRAMMARS or other family-keyed behavior map (not allowlisted)

    A small allowlist covers metadata-only references (trace fields, package report tags, audit logs). The allowlist lives in tests/contract/_family_dispatch_allowlist.py and entries require a reason comment. Cycle 3's "decommission acceptance" check uses this test — not a grep.

    12. Cross-Cycle Parallelization (Authoritative Sequencing)¶

    This section is the authoritative sequencing reference. Where the diagram in §3 disagrees, this section wins.

    • Cycle 1 must complete before Cycle 2 starts. Cycle 2 depends on Cycle 1's typed attribute schemas, generator capability manifests, and DomainExtensionManifest. The v1 plan claimed they were orthogonal — that was wrong.
    • Cycles 2 and 3 may overlap. Once Cycle 1's substrate ships, Cycle 2 (kernel capability) and Cycle 3 (recipe decommissioning) operate on orthogonal layers.
    • Cycle 3 cannot complete before Cycle 4 has caught up family-by-family. A migration is "done" only after both ShapeProgram diff AND visible-artifact build pass. Cycles 3 and 4 interleave family-by-family, not sequentially.
    • Cycles 4 and 5 are paired and ship in tightly alternating commits. Each Cycle 4 visible-layer slice gets its Cycle 5 diagnostic immediately after.
    • Cycle 6 cannot start before the DomainExtensionManifest contract from Cycle 1 has been exercised by at least one migration (typically the hard-surface domain registering itself in Cycle 1). Once the contract is proven, each Cycle 6 domain registers independently and can ship in parallel with other domains.
    • Cycles 7 and 8 are strictly gated by their dependencies and do not parallelize backward.

    19. Bottom Line¶

    The northstar is a real, finishable target. This plan sequences it into 66-115 concrete sessions across 8 cycles. Every cycle ships production-grade work. Every cycle defends the stable contracts. Every cycle has a verification floor that prevents "shipping a beta in production paint."

    The work is multi-month to a year of focused engineering, not a single session. But it is finishable, and this plan is the map to finish it.

    The user's principle is honored absolutely: Lathe must be modular, and the key here is procedural generation. We should not specify any specific asset. Cycle 3's decommissioning of _RECIPES is the moment that principle becomes structurally enforced in the codebase. Every cycle after that builds on a procedural foundation that does not know what a "crate" or "door" or "tree" or "humanoid" is — only what primary_volume + panel + fastener or trunk + branch + leaf or joint + bone + skin compose to.

    This plan is the canonical source of truth for completing the northstar. Future implementation agents should pick the next unfinished cycle, execute its session-sized slice, verify, commit, push, and update the audit. The plan does not need to be revisited until a cycle's acceptance criteria are met and the next cycle begins.
